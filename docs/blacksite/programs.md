# Programs — the kernel, Python, JavaScript, the editors

The console is an OS because it runs programs — yours. Write one in the room's editors, keep it in the console's files, and run it under a kernel that keeps the house safe from it and it safe from the house.

## The kernel

Every program — Python, JavaScript, shell script — is admitted to a process table with a pid, a parent, and a state:

- `ps` — processes, live and recent.
- `jobs` — the kernel's live programs.
- `kill <pid>` — stop one; the kernel reclaims it.
- A trailing `&` backgrounds a program (`run x.py &`) so you keep typing.
- `stop` stops whatever the room is running; `halt` stands the whole table down.

The quotas, honestly stated: at most **32 live programs**, spawn trees at most **8 deep**, a burst limit on spawning, an output quota per program, and a **wall clock per run** (a program parked in `input()` waits on you, not the clock, and is exempt). A fork bomb fills the table and dies at the gate; an endless loop stops at its fuel or the kernel's word. These numbers are the room's physics — `limits` in the console lists what the room honestly cannot do, and it is worth reading once.

## Python

`python3 hello.py` — or just `run hello.py` — executes on a real interpreter built for the room: numbers, strings, lists, dicts, tuples, sets, functions, classes with inheritance and `super()`, the dunder protocol (`__str__`, `__len__`, `__iter__`, `__getitem__`, …), lambdas, generators, comprehensions, `nonlocal`, `try/except/else/finally`, f-strings. Beside it, a working library: `math`, `random`, `sys`, `json`, `re`, `collections` (Counter, deque, defaultdict, namedtuple), `itertools`, `functools`, `os` and `os.path` walking the console's own files, `time`, `base64`, `hashlib`, `statistics`, `string` — and the **house module**, the room's own readings as importable data.

Your own `.py` files join in: a helper beside the script, or under `/packages`, imports like anywhere else. Circular loads resolve the way node's do — a loaded file answers with what it has so far. `input()` reads the console line while the program waits. Errors are spoken in Python's own voice.

It is a dialect and says so out loud: **no threads, and no bytes type** — hashes and encodings speak in text and lists of numbers. The same honesty as everything else in the room.

## JavaScript

A real JavaScriptCore engine runs `.js` programs under the same kernel. Packages live in the tree and load by name (`node pkg.js` works too). The room ships one serious piece of machinery on this engine: **real git in the console** (isomorphic-git over the house's own HTTP) — `git clone`, edit the files, commit, push back, and the `gh` client beside it (sign-in, repos, issues, pull requests). There are also OpenAI-shaped clients (the `ask xai` and `ask any` programs on the wheel) for houses that keep such keys.

## Files and editors

The console's own tree is a real little filesystem: text files, folders, the `/packages` shelf, homes for captures and deliverables staged from the room. The everyday Unix of it — `ls`, `cat`, `cp`, `mv`, `rm`, `mkdir`, `grep`, `head`, `tail`, `wc`, and friends — is all in [commands.md](commands.md), and pipes and redirects work the way you expect: a run's output can be appended to a file, commands chain with `;` and `&&`, and `$(...)` speaks what it ran.

Two editors live in the room, each with its personality kept: a **vim** (modes, motions, `:` line, search) and an **emacs** (chords, the minibuffer). Both edit the console's files in place on glass. If you learned one editor's fingers long ago, they still work here.
